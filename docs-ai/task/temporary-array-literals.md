## 1. 背景・動機

### 1.1 現状の制約

現在の nospace では、配列や文字列を関数に渡すには変数宣言が必要：

```nospace
func: __main() {
  let: msg[]("Hello");
  puts(msg);              # 変数 msg を経由する必要がある #
}
```

これは冗長であり、C の `puts("Hello")` や Python の `print([1, 2, 3])` のように直接記述したい。

### 1.2 目標

以下の構文を実現する：

```nospace
puts("Hello");           # 文字列リテラルを直接渡す #
print([1, 2, 3]);        # 配列リテラルを直接渡す #
```

リテラル式は **配列の先頭アドレス（参照）** を返す（= `int` 型）。

---

## 2. 構文設計

### 2.1 文字列リテラル式

既存のトークン `StringLiteral` を式の位置でも使用可能にする。

```bnf
expr_val ::=
    | ...
    | string_literal          # 文字列リテラル式（新規）
```

```nospace
puts("Hello");              # "Hello\0" の先頭アドレスを返す #
let: p; p = "Hello";        # p に先頭アドレスを代入 #
__putc(*"ABC");             # 'A' (65) を出力 #
```

- ヌル終端は自動追加される（既存の `StringLiteral` トークンと同じ）
- 式の型は `int`（アドレスを表す整数）
- `"Hello"` は 6 スロット（5文字 + ヌル終端）を占有する

### 2.2 配列リテラル式

```bnf
expr_val ::=
    | ...
    | "[" expr ("," expr)* "]"   # 配列リテラル式（新規）
```

```nospace
print([1, 2, 3]);           # [1,2,3] の先頭アドレスを返す #
let: p; p = [10, 20, 30];   # p に先頭アドレスを代入 #
*([5, 10, 15] + 1);         # 10 を取得 #
```

- 配列リテラルはヌル終端を追加しない
- 式の型は `int`（アドレスを表す整数）
- `[1, 2, 3]` は 3 スロットを占有する
- 要素は定数でなくてもよい（ランタイム式も可）

### 2.3 tree_parser の変更

`Expression` に新しいバリアントを追加：

```rust
pub enum Expression {
    // ... 既存バリアント ...
    StringLiteral(Vec<i64>),           // 文字列リテラル式
    ArrayLiteral(Vec<Box<LocatedExpression>>),  // 配列リテラル式
}
```

- `StringLiteral`: トークナイザが既にパースした文字コード列を保持
- `ArrayLiteral`: 各要素が任意の式（ランタイム評価可能）

## 3. 候補1: 文スコープ一時配列

**コンセプト**: リテラル式は、それを含む文の評価中のみ有効な一時メモリ領域に配列を確保する。文の評価が終了したら、その領域は破棄（再利用可能）される。C++ の右辺値 `std::vector` に相当。

### 3.1 semantic_analyzer の変更

```rust
pub(crate) enum ExecExpression {
    // ... 既存バリアント ...
    /// 一時文字列リテラル: (文字コード列, 一時スロットオフセット, スロット数)
    TempStringLiteral(Vec<i64>, usize, usize),
    /// 一時配列リテラル: (要素式リスト, 一時スロットオフセット, スロット数)
    TempArrayLiteral(Vec<Box<LocatedExecExpression>>, usize, usize),
}
```

意味解析フェーズで各文をスキャンし、文に含まれる一時リテラルを検出する。各一時リテラルに対して「一時スロットオフセット」を割り当てる。この情報は ExecExpression に埋め込まれる。

一時スロットの管理：
- 各 Block（スコープ）に `temp_slot_count: usize` フィールドを追加
- 一時スロットは通常の変数スロットの後に配置される
- 同じ文に複数の一時リテラルがある場合、それぞれ別のオフセットを持つ
- 異なる文の一時リテラルは同じオフセットを共有できる（再利用）

### 3.2 interpreter の変更

```rust
pub(super) struct LocalEnvironment<'a, 'aenv> {
    // ... 既存フィールド ...
    /// 一時配列領域
    temp_storage: Vec<i64>,
}
```

- `enter_block()` 時に `temp_storage` をリサイズ（必要な最大一時スロット数に）
- 一時リテラル評価時：
  1. `temp_storage[offset..offset+size]` に値を書き込む
  2. `temp_storage` 領域のアドレスを返す
- 文の終了後、`temp_storage` はクリアしない（次の文で上書きされる）

アドレス解決の課題：
- `get_by_address` / `set_by_address` が `temp_storage` 領域もカバーする必要がある
- 既存のアドレス空間: `global_variables` → `scope_stack[0]` → `scope_stack[1]` → ...
- 一時領域をどこに配置するか？
  - 案A: 各スコープの末尾に一時スロットを含める（`variable_count` に加算）
  - 案B: 別のアドレス空間に置く（アドレス体系の変更が必要）
- **案A を採用**: `variable_count` にスコープごとの最大一時スロット数を加算。一時リテラルはスコープの `variables` の後のスロットにマッピングされる。

### 3.3 compiler_ws の変更

- 関数のローカルヒープサイズに一時スロット分を加算
- 一時リテラル評価時：
  1. ローカルヒープ上の一時スロットにストア命令を生成
  2. 一時スロットのアドレスをスタックにプッシュ
- 文字列リテラルの場合、毎回ストア命令列を生成
  - 例: `"Hello"` → 6回の HeapStore + アドレスプッシュ
  - ループ内で使う場合、毎イテレーションで初期化コードが実行される

### 3.4 ライフタイムのルール

```
┌─ 文1: puts("Hello");
│   "Hello\0" を temp_storage[0..6] に確保
│   puts にアドレスを渡す
│   puts が実行される
│   → 文1 終了: temp_storage[0..6] は無効（次の文で上書き可能）
└─
┌─ 文2: __putc(*p);
│   もし p が "Hello" のアドレスを保持していたら → 未定義動作
└─
```

## 4. 候補2: 無名static変数

**コンセプト**: リテラル式は、コンパイル時に無名の static 変数として割り当てられる。エントリーポイント呼び出し前に初期化され、プログラム終了まで存続する。C や Java の文字列リテラルに相当。

### 4.1 semantic_analyzer の変更

意味解析フェーズで、ソース内の全リテラル式を収集し、無名 static 変数を生成する。

```rust
pub(crate) enum ExecExpression {
    // ... 既存バリアント ...
    /// 無名 static 配列への参照
    /// IdentifierRef はグローバルスコープの無名変数を指す
    StaticArrayRef(IdentifierRef),
}
```

処理手順：
1. AST を走査し、式の位置にあるリテラルを収集
2. 各リテラルに対して `Scope` のグローバルレベルに無名変数を追加
   - 変数名は `__anon_arr_0`, `__anon_arr_1`, ... のような内部名
   - `is_static = true`, `array_size = Some(要素数)`
3. 初期化文を `static_init_statements` に追加
4. リテラル式を `StaticArrayRef(id_ref)` に変換（id_ref は無名変数への参照）

配列リテラル `[expr1, expr2, ...]` の要素が全て定数式の場合：
- 初期化文は通常の配列初期化と同様

配列リテラル `[expr1, expr2, ...]` の要素にランタイム式が含まれる場合：
- 初期化を static_init で行うことは不可能（ランタイム値に依存するため）
- **候補2ではランタイム要素を持つ配列リテラルは制限される**
  - 制限案A: 全要素が定数式でなければコンパイルエラー
  - 制限案B: ランタイム要素がある場合のみ候補1の方式（文スコープ一時）にフォールバック
  - 制限案C: 文字列リテラルのみ候補2、配列リテラルは常に候補1（ハイブリッド）

### 4.2 interpreter の変更

既存の `interpret_global()` で `static_init_statements` が実行されるため、特別な変更は不要。

- 無名 static 変数は `global_variables` の一部として確保される
- `StaticArrayRef(id_ref)` は既存の `Variable(id_ref)` と同様にアドレスを解決
  - 実際には `ExecExpression::Variable(id_ref)` を生成すれば十分（`StaticArrayRef` は不要かもしれない）

→ 方式の簡潔さ: 意味解析で無名変数を追加し、既存の `Variable` 参照に変換するだけで、インタプリタの変更は一切不要。

### 4.3 compiler_ws の変更

既存の static 変数のコード生成インフラをそのまま利用可能。

- 無名 static 変数はグローバルヒープ上に配置される
- 初期化コードは `static_init_statements` で一度だけ生成・実行される
- 使用箇所では、グローバルヒープ上のアドレスを Push するだけ

### 4.4 ライフタイムのルール

```
──── プログラム開始 ────
  "Hello\0" が global_variables[offset..offset+6] に初期化される（static_init）
──── __main 開始 ────
┌─ 文1: puts("Hello");
│   puts にアドレスを渡す（global_variables[offset]）
│   puts が実行される
└─
┌─ 文2: let: p; p = "Hello";
│   同じ "Hello" のアドレスを p に代入 *1
│   → p は安全に後で使用可能
└─
┌─ 文3: __putc(*p);
│   'H' (72) を出力 → 安全
└─
──── プログラム終了 ────

*1: 同じリテラル文字列 "Hello" を共有する最適化は将来的に可能。
    現時点ではリテラルごとに別の無名変数を割り当てるのが安全。
```

## 5. シナリオ分析

各候補がどう振る舞うかを具体的なシナリオで比較する。

### 5.1 基本的な使用

```nospace
puts("Hello");
```

| 項目 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| メモリ配置 | ローカルヒープ/スタック上 | グローバルヒープ上 |
| 初期化タイミング | 文の実行時に毎回 | プログラム開始時に1回 |
| 解放タイミング | 文の終了後 | プログラム終了時 |
| 動作 | 正常 | 正常 |

### 5.2 ループ内のリテラル

```nospace
repeat: i(0), 100, puts("tick");
```

| 項目 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| 初期化回数 | 100回（毎イテレーション） | 1回 |
| メモリ使用量 | 固定（再利用） | 固定（1回分） |
| WS命令数 | 多い（毎回ストア生成） | 少ない（アドレスPushのみ） |

候補2が効率的。

### 5.3 アドレスの保存と再利用

```nospace
let: p;
p = "Hello";
# ... 数行後 ... #
__putc(*p);    # p は有効か？ #
```

| 項目 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| 安全性 | ❌ 未定義動作（p がダングリング） | ✅ 安全（static 変数は存続） |

候補2が安全。

### 5.4 関数への参照渡しと保持

```nospace
func: store_ref(ref) {
  static: saved_ref;
  saved_ref = ref;
}

func: __main() {
  store_ref("Hello");
  # ... 後で saved_ref を使う #
}
```

| 項目 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| 安全性 | ❌ saved_ref がダングリング | ✅ 安全 |

候補2が安全。

### 5.5 リテラルの書き換え

```nospace
*"Hello" = 'B';    # 'H' を 'B' に書き換え #
puts("Hello");     # 何が出力される？ #
```

| 項目 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| 1回目の puts | "Bello" | "Bello" |
| 2回目の puts("Hello") | "Hello"（再初期化される） | "Bello"（書き換え永続） |

- 候補1: 毎回初期化されるため書き換えは一時的。ただし同一文内では反映される。
- 候補2: static 変数なので書き換えが永続する。これは C 言語での文字列リテラル書き換え（未定義動作）と類似の問題。将来的に `const` 実装で禁止予定。

### 5.6 関数の戻り値としてのリテラル

```nospace
func: get_greeting() {
  return: "Hello";
}
```

| 項目 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| 動作 | ❌ 危険: 関数のスコープ終了で一時領域は無効化。呼び出し元がアドレスを使うと未定義動作 | ✅ 安全: グローバルな static 変数への参照を返すので有効 |

候補2が安全。

### 5.7 配列リテラルにランタイム式を含む場合

```nospace
let: x(5);
print([x, x+1, x+2]);
```

| 項目 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| 対応 | ✅ 自然に対応可能（毎回評価） | ❌ static 初期化時にランタイム値が不可。制限 or ハイブリッド方式が必要 |

候補1が自然。候補2ではこのケースに対応するために追加の設計が必要。

## 6. 設計上の比較

### 6.1 実装の複雑さ

| コンポーネント | 候補1（一時） | 候補2（static） |
|---------------|-------------|----------------|
| tree_parser | 中（共通: 式位置でのリテラルパース） | 中（共通） |
| semantic_analyzer | 高（文ごとの一時スロット管理、オフセット計算） | 中（無名変数生成、static_init への追加） |
| interpreter | 中-高（一時領域管理、アドレス解決拡張） | 低（既存インフラで対応可能、変更ほぼ不要） |
| compiler_ws | 高（ローカルヒープ拡張、毎回のストア命令生成） | 低（既存の static 変数コード生成で対応可能） |
| optimizer | 中（一時リテラルの最適化パス追加検討） | 低（既存の最適化パスが適用可能） |

候補2の実装コストが大幅に低い。

### 6.2 アーキテクチャへの影響

**候補1:**
- `LocalEnvironment` に一時領域の概念を追加（新しいメモリ管理の概念）
- アドレス空間の拡張（`get_by_address` / `set_by_address` の変更）
- 文レベルのライフタイム管理（新しい概念の導入）
- WS コンパイラのローカルヒープサイズ計算の変更

**候補2:**
- 意味解析で無名変数を生成するのみ
- 既存の `static` 変数・`global_variables` の仕組みを再利用
- アドレス空間の変更なし
- 新しいメモリ管理概念の導入なし

候補2はアーキテクチャへの侵襲性が低い。

### 6.3 一貫性

**候補1:**
- `let: msg[]("Hello");` の `msg` は変数スコープに従う
- `"Hello"` (リテラル式) は文スコープに従う
- 同じ `"Hello"` でも文脈で異なるライフタイムを持つ → やや紛らわしい

**候補2:**
- `let: msg[]("Hello");` の `msg` は変数スコープに従う
- `"Hello"` (リテラル式) は static 変数と同じライフタイム
- `static: msg[]("Hello");` と類似の挙動 → 一貫性が高い

### 6.4 Whitespace コンパイルコスト

**候補1 — `puts("Hello")` のWS生成コード:**
```
# 毎回: temp スロットに "Hello\0" を書き込む (12命令) #
Push temp_addr;   Push 72; Store;    # 'H' #
Push temp_addr+1; Push 101; Store;   # 'e' #
Push temp_addr+2; Push 108; Store;   # 'l' #
Push temp_addr+3; Push 108; Store;   # 'l' #
Push temp_addr+4; Push 111; Store;   # 'o' #
Push temp_addr+5; Push 0; Store;     # '\0' #
Push temp_addr;                       # アドレスをスタックに #
Call puts;
```

**候補2 — `puts("Hello")` のWS生成コード:**
```
# 初期化 (1回だけ、static_init フェーズ) #
Push global_addr;   Push 72; Store;    # 'H' #
Push global_addr+1; Push 101; Store;   # 'e' #
... (同上)
# 使用箇所 (毎回: 1命令) #
Push global_addr;                      # アドレスをスタックに #
Call puts;
```

候補2は使用箇所のコードサイズが大幅に小さい。ループ内では差が顕著になる。

## 7. 実運用上の比較

### 7.1 メモリ効率

| 観点 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| ピーク使用量 | 低い（必要時のみ確保） | やや高い（全リテラルが常駐） |
| ループ内 | 効率的（再利用） | 効率的（1回のみ初期化） |
| 多数のリテラル | 文ごとに最大値のみ必要 | 全リテラル分のグローバルメモリ |

- 候補1はピークメモリが小さいが、初期化コストが高い
- 候補2はメモリが常駐するが、初期化コストが低い
- 典型的なプログラムでは、リテラルの合計サイズは小さいためメモリ差は軽微

### 7.2 実行速度

| 観点 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| 初回 | やや遅い（初期化コスト） | 起動時に初期化 |
| ループ内 | 遅い（毎回初期化） | 高速（アドレスのみ） |
| 関数呼び出し | やや遅い | 高速 |

候補2が一般的に高速。

### 7.3 安全性

| 観点 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| ダングリングポインタ | ❌ 発生しやすい | ✅ 発生しない |
| リテラル書き換え | 一時的（影響限定） | 永続的（危険） |
| 関数越え参照 | ❌ 危険 | ✅ 安全 |

- 候補1はダングリングポインタのリスクが高く、プログラマのミスを誘発しやすい
- 候補2はリテラル書き換えのリスクがあるが、将来の `const` 実装で解決可能

### 7.4 ユーザー体験

| 観点 | 候補1（一時） | 候補2（static） |
|------|-------------|----------------|
| 直感性 | C++ 的（値セマンティクス） | C/Java 的（参照セマンティクス） |
| 落とし穴 | 「文を跨ぐとダメ」が分かりにくい | 「書き換えが残る」が分かりにくい（const 未実装時） |
| 学習コスト | 高い（ライフタイムの概念必要） | 低い（C 文字列と同じ） |
| エラーの深刻度 | 高い（サイレントバグ） | 低い（const 違反は検出可能） |

## 8. 結論・推奨

### 8.1 総合比較まとめ

| 評価軸 | 候補1（一時） | 候補2（static） | 優位 |
|--------|-------------|----------------|------|
| 実装コスト | 高 | 低 | **候補2** |
| アーキテクチャ侵襲性 | 高 | 低 | **候補2** |
| 安全性（ダングリング） | 低 | 高 | **候補2** |
| 安全性（書き換え） | 高 | 中（const 未実装） | 候補1 |
| WS コンパイル効率 | 低 | 高 | **候補2** |
| メモリ効率 | やや良い | やや劣る | 候補1（差は軽微） |
| ランタイム式の配列対応 | 自然 | 要追加設計 | 候補1 |
| 一貫性 | やや低い | 高い | **候補2** |
| ユーザー体験 | C++ 的 | C/Java 的 | **候補2** |

### 8.2 推奨

**候補2（無名 static 変数方式）を基本戦略として推奨する。**

理由：
1. 実装コストが大幅に低い（既存の static 変数インフラを再利用）
2. ダングリングポインタが発生しない（最も深刻なバグクラスを回避）
3. WS コンパイル時のコードサイズが小さい
4. C/Java の文字列リテラルと同じ直感的なセマンティクス

ただし、以下の制限と対策が必要：

- **文字列リテラル**: 全て定数なので候補2で完全対応可能
- **配列リテラル（全要素が定数式）**: 候補2で完全対応可能
- **配列リテラル（ランタイム要素含む）**: 候補2では直接対応不可
  - 対策案1: コンパイルエラーにする（定数式のみ許可）
  - 対策案2: ランタイム要素を含む配列リテラルのみ候補1方式にフォールバック（ハイブリッド）
  - 対策案3: 初期実装では配列リテラルをサポートせず、文字列リテラルのみ対応

### 8.3 段階的実装の提案

1. **Phase 1**: 文字列リテラル式のみ候補2で実装（最もユースケースが多い）
2. **Phase 2**: 定数配列リテラル式を候補2で実装
3. **Phase 3**: （必要に応じて）ランタイム要素配列リテラルをハイブリッド方式で対応
