# 02: 案 B（サイズ上限）— 実施しない。実施する場合の検査箇所

案 B（配列・struct のサイズに上限を設ける）は実施しない。ここには不採用の理由、仮に実施する場合にどこへ上限の検査を入れるか、実施しない場合に残る懸念を記録する。

作成日: 2026-10-19
ステータス: 不採用（記録のみ）

## 実施しない理由

- 案 A だけで、指摘された症状（debug の panic、release の wrap による誤ったコード）はすべて解消する
- WhitespaceVM のヒープは `HashMap<i64, i64>` で、宣言しただけの巨大な配列はメモリを消費しない。使ったメモリ量は実行時に `max_memory_cells`（[ws-vm-run-mode-support/01](../ws-vm-run-mode-support/01-memory-limit.md)）で制限できる
- 上限値は言語仕様になる。値の根拠（ヒープ空間の想定）が今は決まっておらず、決めると将来の変更が互換性の問題になる
- 上限を入れても、以下の表のとおり検査箇所は案 A とほぼ同じで、案 A を省略できるわけではない

## 仮に案 B を実施する場合の検査箇所

### 上限の種類

「1 つの配列が大きい」だけを制限しても足りない。上限以下の配列を多数宣言すれば合計は溢れるので、**合計にも上限が要る**。必要な上限は次の 4 つ（1 つの値 `MAX_SIZE_SLOTS` で兼ねてもよい）。

| 上限 | 対象 | 検査が必要な理由 |
|---|---|---|
| U1: 要素数 | `[N]` の `N` | 宣言の段階で早く・位置付きで弾くため。U2 があれば理論上は不要 |
| U2: 型のサイズ | 配列型 `T[N]` のサイズ（要素数 × 要素サイズ）、struct の `total_size` | 多次元配列・struct の入れ子で掛け算が重なる |
| U3: スコープの合計 | 1 つのスコープの `variable_count` | 上限以下の変数が多数あると溢れる |
| U4: 領域の合計 | 関数フレームの合計（ネストしたブロックを含む）、グローバル + static の合計、ルートレベルのブロックの合計、static 初期化子のブロックの合計 | スコープごとの検査では、ネストしたブロックの合計・関数内 static の合計を防げない |
| U5: 領域の組み合わせ | `GLOBAL_PTR` + グローバル領域 + 関数フレーム ×（呼び出しの深さ） | ローカルフレームはグローバル領域の直後（`LOCAL_HEAP_END`、`bump.rs:27-31`）に積まれる。U4 の各合計が単独で収まっても、足すと溢れる |

### 検査を入れる箇所

案 A の `checked_add` / `checked_mul` の箇所に加えて、以下に「上限を超えたらエラー」の比較を入れる。checked 演算は残す（上限検査の前に溢れるのを防ぐため。上限以下の値同士でも、掛け算・足し算の途中は溢れうる）。

| # | 箇所 | 上限 | 備考 |
|---|---|---|---|
| 1 | パーサ: `parse_array_size`（変数の `[N]`）、`parse_type_spec`（`@T[N]`、2 箇所。[tree-parser-dedup](../tree-parser-dedup/README.md) 後は 1 箇所）、struct フィールドの `name[N]` | U1 | 既存の `array size must be positive` と同じ場所。トークン位置付きで報告できる |
| 2 | パーサ: 文字列初期化 `parse_array_string_init`（`statement/mod.rs` の `string_size = chars.len() + 1`）、配列リストの要素数からのサイズ推論 `parse_array_list_init`（`let: a[] = (...)`） | U1 | `[]` でサイズを省略したとき、サイズは初期化子から決まり #1 を通らない |
| 3 | 意味解析: `mod.rs:694`（変数宣言の要素数） | U1 | #1・#2 を通った値だが、パーサ以外（テストや将来の AST 生成）からの入力に備えるなら置く |
| 4 | 意味解析: `value_type_size`（`mod.rs:1016` の掛け算の結果） | U2 | 多次元配列 `@int[N][M]` もここで検査される |
| 5 | 意味解析: `resolve_struct_definition`（`mod.rs:940` の累積の結果 = `total_size`） | U2 | |
| 6 | 意味解析: `scan_variable_declarations`（`mod.rs:721` 付近、`effective_array_size` の確定後） | U2 | struct 型の変数は `total_size` がそのままスロット数になる。現状は配列型変数のスロット数が要素サイズを掛けていない（[README](README.md) の潜在問題）。直すなら `value_type_size` 相当で計算してから検査する |
| 7 | 意味解析: `mod.rs:212`（スコープ内の累積の結果 = `variable_count`） | U3 | `scope.rs:710` は同じ値なので不要 |
| 8 | compiler_ws: `calculate_total_variable_count`（`statement.rs:418`）の結果 | U4 | 関数フレームの合計。ネストしたブロックの合計はここでしか分からない |
| 9 | compiler_ws: `compute_static_var_offsets`（`context.rs:28`）の結果と、グローバルの `variable_count` の合計（`global_heap_size`） | U4 | 関数内 static は全関数分がグローバル領域に積まれるので、ここでしか分からない |
| 10 | compiler_ws: `enter_block_scope`（`context.rs:324`）後の `next_var_offset`。グローバルのコンテキスト（ルートレベルのブロック）と static 初期化のコンテキスト | U4 | この 2 経路は #8・#9 のどちらの合計にも含まれない |
| 11 | compiler_ws: `GLOBAL_PTR + global_heap_size + 関数フレーム`（関数ごと、または最大フレーム） | U5 | 再帰の深さはコンパイル時に分からないので、深さ 1 のぶんだけを検査し、残りは下記「上限値の決め方」で実行時の上限と組み合わせて保証する |
| 12 | `docs/spec.md` | — | 上限値と、超えた場合はコンパイルエラーであることを記載 |

- #8・#9 は compiler_ws にあるので、ターゲットが WS 以外（将来の [wasm-js-compiler](../wasm-js-compiler/)）では別途必要になる。言語仕様として上限を定めるなら、意味解析で計算できるよう、フレーム合計とグローバル領域の合計の計算を意味解析に移すのが望ましい（そのぶん変更範囲が広がる）
- 上限検査が不要な箇所: `GLOBAL_PTR + offset`（`expression.rs:132`、`169`）、`bump.rs:30` / `fsba.rs:647` は #9 の合計以下なので不要

### 上限値の決め方（参考）

フレームの上限を `L`、`max_memory_cells` を `M` とする。呼び出しごとに少なくとも 1 セルは使うので、呼び出しの深さは `M` 以下、フレームポインタは `L × M` 程度に収まる。`GLOBAL_PTR + グローバル領域の上限 + L × M < i64::MAX` となるよう `L` を選べば、U5 が保証され、実行時のフレームポインタの wrap（下記）も防げる。逆に言えば、これが案 B を実施する主な動機になる。

## 案 B を実施しない場合に残る懸念

- **実行時のフレームポインタの wrap**: ローカルフレームはグローバル領域の直後に積まれる。グローバル領域と関数フレームがどちらも単独で `i64` に収まっていても、再帰が無くても、その合計でフレームポインタ（`frame + local_heap_size`）が wrap して負のアドレスになりうる（例: グローバル `g[i64::MAX-100]` と `__main` 内の `a[i64::MAX-100]`）。再帰があれば、より小さいフレームでも起きる。WS の算術は wrap する仕様で、ヒープは負のアドレスも受け付けるため、エラーにならず別の領域と重なる。`--std-ext debug` 有効時は `-10`〜`-13`（`__trace` / `__assert` / `__clog` のフック）に当たる可能性もある。`max_memory_cells` は使ったセル数を数えるので、この wrap は検出できない
  - 現実的なプログラムでは起きない（`i64::MAX` に近い配列を宣言して再帰する必要がある）ので、懸念として記録するに留める
  - 対策が必要になったら、上記の「上限値の決め方」で案 B を実施するか、VM にアドレス範囲の検査を入れる
- **直接実行インタプリタの巨大確保**: `let: a[9223372036854775807];` は直接実行インタプリタで `capacity overflow` の panic になる。[retire-direct-interpreter](../retire-direct-interpreter/README.md) で廃止されるまで残る
