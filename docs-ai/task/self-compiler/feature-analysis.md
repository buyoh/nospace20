# セルフコンパイラ向け機能分析

nospace の各機能について、セルフコンパイラ実装における必要性を分析し、nospace-core への採用・除外を根拠付きで整理する。

---

## 1 採用した機能

### 1.1 数値リテラル（10進・16進）

**必要度: 必須**

- 10進数: 定数値、配列サイズ、テーブルサイズ等の指定
- 16進数: ASCII コードの直接指定、ビットパターンの記述に重要

セルフコンパイラでは文字コードの比較（例: `c >= 0x30 && c <= 0x39` で数字判定）を多用するため、16進リテラルは利便性が高い。

### 1.2 文字リテラル

**必要度: 必須**

字句解析で文字の分類に必須。例:
- `'A'` ～ `'Z'` の範囲判定で識別子を認識
- `'+'`, `'-'` 等で演算子トークンを識別
- `'\n'` で改行出力

### 1.3 配列

**必要度: 必須**

セルフコンパイラのデータ構造の基盤。以下に使用:

| 用途 | 説明 |
|------|------|
| ソースバッファ | `let: src[MAX_SRC];` で入力ソース全体を保持 |
| トークン配列 | `let: tok_type[MAX_TOK]; let: tok_val[MAX_TOK];` |
| AST ノード | アリーナアロケーション: `let: node_type[MAX_NODE]; let: node_left[MAX_NODE]; let: node_right[MAX_NODE];` |
| シンボルテーブル | `let: sym_name[MAX_SYM * MAX_NAME_LEN];` |
| 出力バッファ | 必要に応じた出力バッファリング |

配列初期化（`let: arr[3](1, 2, 3);`）も、テーブル初期化等に有用。

### 1.4 参照・間接参照

**必要度: 必須**

- 配列を関数に渡す際に参照（`&arr`）が必要
- 参照経由のアクセス（`*p`, `*(p + i)`）でデータ構造を操作
- swap 関数等のユーティリティに不可欠

```
# 配列を関数に渡す典型的パターン #
func: strlen(s) {
    let: i(0);
    while: *(s + i) {
        i += 1;
    };
    return: i;
}

func: main() {
    let: buf[16];
    # ... buf に文字列を格納 ... #
    __puti(strlen(&buf));
}
```

### 1.5 関数・再帰

**必要度: 必須**

- コンパイラのモジュール構造（字句解析、構文解析、コード生成）を関数に分離
- 再帰下降パーサーの実装に再帰が不可欠

### 1.6 制御構文 (if/else, while, break, continue)

**必要度: 必須**

全てコンパイラの実装に不可欠:
- `if/else`: トークン種別による分岐、エラー処理
- `while`: 入力読み取りループ、トークン列の走査
- `break`: ループからの早期脱出
- `continue`: 条件スキップ

### 1.7 比較・論理演算子

**必要度: 必須**

条件分岐の判定に不可欠。特に:
- `==`, `!=`: トークン種別の比較
- `<`, `>=`: 文字コード範囲の判定
- `&&`, `||`: 複合条件（例: `c >= 'a' && c <= 'z'`）
- `!`: 条件反転

### 1.8 複合代入演算子

**必要度: 推奨**

`+=`, `-=` 等はシンタックスシュガーだが、コンパイラ実装で頻繁に使用するパターンであり、可読性向上に寄与。例: `pos += 1;`

内部的に `x = x + y` に展開されるため、コンパイラの実装コストはごく小さい。

### 1.9 I/O 組み込み関数

**必要度: 必須**

| 関数 | セルフコンパイラでの使用 |
|------|------------------------|
| `__getc()` | ソースコード読み取り |
| `__putc(x)` | ターゲットコードの出力 |
| `__puti(x)` | 数値の出力（エラーメッセージ等に位置情報を含める） |
| `__geti()` | 数値入力（使用頻度は低いが含めてよい） |

### 1.10 グローバル変数

**必要度: 必須**

セルフコンパイラのグローバル状態の管理に必要:
- ソースバッファ全体
- トークン配列
- AST ノードプール
- 現在の読み取り位置
- エラー状態

グローバル変数がなければ、全ての状態を関数引数で渡す必要があり、引数の数が爆発する。

## 2 除外した機能

### 2.1 ブロックスコープ変数

**除外理由: コンパイラの実装複雑度を大幅に削減**

ブロックスコープでは、if/while ブロック内の `let:` が新しいスコープを作成する。これをサポートするには:

1. **スコープスタックの管理**: ブロック進入・退出時のスコープ切り替え
2. **変数の寿命管理**: ブロック終了時の変数破棄
3. **シャドウイング**: 同名変数の解決
4. **メモリレイアウト**: 動的なスタックフレーム管理

これらは全て、セルフコンパイラの実装を著しく複雑にする。

**代替**: 全ての `let:` を関数の先頭に記述する。この書き方は JavaScript の `var` と同様のホイスティング動作であり、nospace でも有効。

```
# nospace-core スタイル #
func: example() {
    let: i, found;
    i = 0;
    found = 0;
    while: i < 10 {
        if: check(i) {
            found = 1;
        };
        i += 1;
    };
}
```

### 2.2 static 変数

**除外理由: メモリ管理の簡略化**

static 変数は関数呼び出しをまたいで値を保持する。これのサポートには:

1. **グローバルメモリ領域の別管理**: static 用メモリの初期化タイミング制御
2. **初期化の分離**: 関数呼び出し時ではなくプログラム開始時の初期化

**代替**: グローバル変数で代替可能。static が使われる典型的なケース（カウンタ、状態保持）はグローバル変数で実現できる。

### 2.3 ネストした関数定義

**除外理由: 名前解決の簡略化**

ネストした関数定義のサポートには:

1. **スコープの入れ子管理**: どのスコープのどの関数が見えるかの解決
2. **関数のホイスティング**: ネストしたスコープ内でのホイスティング
3. **コード生成の複雑化**: ネストした関数のコード配置

**代替**: 全ての関数をトップレベルに定義する。名前の衝突を避けるためにプレフィックスを使う慣習を設ける。

```
# nospace-core スタイル #
func: parser_parse_expr() { ... }
func: parser_parse_stmt() { ... }
func: lexer_next_token() { ... }
func: codegen_emit() { ... }
```

### 2.4 文字列リテラル

**除外理由: 未実装機能の対象外**

nospace 本体でも未実装のため、nospace-core にも含めない。

**代替**: 文字配列を手動で構築する。

```
# "let:" を手動で構築 #
func: match_let(s) {
    return: *(s) == 'l' && *(s+1) == 'e' && *(s+2) == 't';
}
```

キーワードテーブルを配列初期化で定義する方法も有効:

```
let: kw_let[4]('l', 'e', 't', 0);
let: kw_func[5]('f', 'u', 'n', 'c', 0);
```

### 2.5 デバッグ用組み込み関数

**除外理由: コンパイラ仕様の簡略化**

- `__clog`, `__assert`: セルフコンパイラの開発時には使用してよいが、nospace-core コンパイラがこれらを認識・コンパイルする必要はない。
- `__assert_not`: `!` と `__assert` の組み合わせで代替可能。
- `__trace`: テスト用であり、コンパイラには不要。

**注意**: セルフコンパイラの開発段階では、nospace のフルインタプリタ上で `__clog` 等を自由に使ってデバッグしてよい。最終的にセルフコンパイラ自身がコンパイルする対象に含めなければよい。

### 2.6 final/const, 型システム

**除外理由: 未実装機能の対象外**

nospace 本体でも未実装のため、検討対象外。

## 3 設計判断のまとめ

### 3.1 最小性と実用性のバランス

nospace-core は「セルフコンパイラが実現可能な最小限の仕様」ではなく、「セルフコンパイラが実現可能で、かつ実用的に記述可能な仕様」を目指す。

例えば、複合代入演算子は技術的には不要だが、コンパイラコードの可読性に大きく寄与するため含める。同様に、16進リテラルも必須ではないが、文字コードの扱いに有用なため含める。

### 3.2 除外基準

以下のいずれかに該当する機能を除外した:

1. **コンパイラの実装複雑度を大幅に増す**: ブロックスコープ、ネスト関数
2. **代替手段があり、利用頻度が低い**: static 変数
3. **未実装**: 文字列リテラル、型システム、final/const
4. **デバッグ・テスト専用**: `__trace`, `__assert_not`

### 3.3 互換性の保証

全ての除外は「機能を使用しない」という制限であり、動作の変更ではない:

- ブロックスコープを使わず、全ての `let:` を関数トップに書く → nospace でも有効
- ネスト関数を使わず、全関数をトップレベルに書く → nospace でも有効
- `static:` を使わず、グローバル変数を使う → nospace でも有効

## 4 セルフコンパイラ実装上の課題

nospace-core の仕様は十分だが、セルフコンパイラの実装にはいくつかの技術的課題がある。これらは仕様の問題ではなく実装上の課題である。

### 4.1 動的メモリ管理の不在

nospace には動的メモリアロケーション（malloc/free）がないため、全てのデータ構造を固定長配列で実現する必要がある。

**対策**: コンパイル対象のプログラムサイズに上限を設け、十分に大きな固定配列を確保する。

### 4.2 文字列操作の冗長性

文字列リテラルがないため、キーワードの比較等が冗長になる。

**対策**: 文字列操作ユーティリティ関数群を定義する（`strcmp`, `strcpy`, `strlen` 相当）。
キーワードはグローバル配列でテーブル化する。

### 4.3 コンパイルターゲットの選択

セルフコンパイラが出力するターゲットコードの形式は、本仕様では規定しない。候補:

1. **Whitespace**: 既存のコンパイラターゲットと一致
2. **nospace → nospace トランスパイラ**: 妥当性検証が容易
3. **独自中間表現**: 段階的に発展可能

ターゲットの選択はセルフコンパイラの実装タスクで決定する。
