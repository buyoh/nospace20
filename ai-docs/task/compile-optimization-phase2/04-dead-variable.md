# 未使用変数削除 (`dead-variable`)

## 概要

定義されたが一度も使用されない変数を検出し、初期化コード生成とメモリ割り当てを省略する。

## 背景

`docs/optimize.md` でも「未使用変数の削除は現在未対応」と記載されている。Phase 1 の `dead-code` パスは未使用関数を削除するが、変数は対象外。

## 難易度が高い理由

1. **変数のスロットインデックス再計算**: 変数を削除するとスロットインデックスが変わり、他の全ての `IdentifierRef.local_index` を更新する必要がある
2. **配列の参照解析**: `&arr` による間接参照を通じて使用されるケースの検出が困難
3. **初期化の副作用**: `let: x(some_function());` のような副作用のある初期化式は、変数が未使用でも実行が必要

## 設計（段階的アプローチ）

### フェーズ 1: 使用解析のみ（警告出力）

実装前の準備段階として、未使用変数を検出して報告する仕組みを導入する。実際の削除は行わない。

- 各変数について、代入以外の読み出し参照を追跡
- 読み出し参照が 0 の変数を「未使用」として報告
- `&var` による参照取得は「使用」とみなす

### フェーズ 2: 初期化コード省略

スロットインデックスの再計算は行わず、未使用変数の**初期化コード生成のみ**をスキップする。

- 変数のスロットは確保するが、初期値の計算を省略
- 副作用のない初期化式のみ対象（定数リテラル、変数参照など）
- スロットインデックスの変更が不要なため、安全に実装可能

### フェーズ 3: 完全削除（将来）

スロットの完全削除とインデックス再計算。影響範囲が大きいため、型システム導入後に検討。

## 効果

- 効果は限定的（プログラマが未使用変数を放置することは少ない）
- セルフコンパイラのような自動生成コードでは効果が大きい可能性
- 警告機能としての価値の方が大きい

## 優先度: 低

他の最適化パスと比較して効果が小さく、実装の複雑さが高い。フェーズ 1（警告のみ）から段階的に進めることを推奨。
