# 型システム: ドットアクセスの名前空間との衝突分析

## 問題

構造体のフィールドアクセスと名前空間の修飾名アクセスは、どちらも `.`（ドット）を使用する。

```
s.field          # 構造体フィールドアクセス #
MySpace.x        # 名前空間の修飾名アクセス #
```

## 現状

- **名前空間** ([ai-docs/task/namespace/](../namespace/)): 設計済み・未実装
  - tree_parser の方式B を採用予定: `ident.ident` を tree_parser で結合して単一の修飾名文字列にする
  - 意味解析ではマングルされた名前 `"MySpace.x"` として扱う
- **構造体**: 本タスクで設計中
  - フィールドアクセスは型依存であり、意味解析で型情報からオフセットを計算する

## 衝突の分析

### 構文レベル

`a.b` という構文は、以下のいずれかの意味を持ちうる:

1. **名前空間アクセス**: `a` が名前空間名で、`b` が名前空間内の識別子
2. **構造体フィールドアクセス**: `a` が構造体型の変数で、`b` がフィールド名
3. **両方が成立するケース**: `a` が名前空間名であり、かつ `a` という構造体型の変数がある場合

ケース3について:
- 構造体名は大文字始まり制約がある
- 名前空間名にも同じ制約を設けるかどうか → namespace/spec.md では制約なし
- 名前空間名と変数名は別のシンボル空間に属する
- よって、`A.b` は名前空間 `A` 内の `b` なのか、変数 `A` のフィールド `b` なのか曖昧になりうる

### 意味解析レベルでの区別

名前空間と構造体を区別するために、意味解析で以下の情報が必要:

- `a` が名前空間名として登録されているか
- `a` が変数名として登録されているか、かつその型が構造体か

名前空間と変数は**異なるシンボル種別**なので、通常は一意に解決される。同名の名前空間と変数が存在する場合のみ曖昧になりうるが、同じスコープに同名の識別子を登録するのはエラーとする既存の仕様で防がれる。

## 推奨方針

### tree_parser の統一

名前空間タスクの方式B（tree_parser で `ident.ident` を結合）は、構造体フィールドアクセスと相容れない。構造体フィールドアクセスは型情報に基づくため、tree_parser の段階では名前の結合ができない。

**提案: tree_parser の方式を変更する**

名前空間タスクの方式B を破棄し、以下の統一方式を採用する:

1. tree_parser は `.` を見たら常に `Expression::DotAccess(base_expr, field_name)` を生成する
   - チェーン `a.b.c` は `DotAccess(DotAccess(a, "b"), "c")` となる

2. 意味解析で `DotAccess` を解決する:
   - `base_expr` が識別子で、それが名前空間名 → マングリングによる名前解決
   - `base_expr` が構造体型の式 → フィールドアクセス（オフセット計算）
   - DotAccess チェーンの途中で名前空間→構造体に切り替わるケース:
     ```
     namespace: A { let: s@Point; }
     A.s.x   → DotAccess(DotAccess(A, "s"), "x")
             → 名前解決: A.s は変数
             → フィールドアクセス: (A.s).x → Point の x フィールド
     ```

3. この方式の利点:
   - tree_parser がシンプル（常に DotAccess を生成）
   - 意味解析で型情報を使って正確に解決
   - 名前空間と構造体の混在に自然に対応

4. この方式の影響:
   - 名前空間タスクの `implementation.md` Step 2 を修正する必要がある
   - 意味解析が `DotAccess` 解決のロジックを持つ必要がある

### 名前空間タスクへの変更要求

名前空間タスクの以下のドキュメントを更新する必要がある:

- `ai-docs/task/namespace/implementation.md` Step 2: 方式B → DotAccess 方式に変更
- `ai-docs/task/namespace/implementation.md` Step 3: 意味解析での DotAccess 解決ロジック追加

## 実装順序

### パターン A: 構造体を先に実装

1. 型システム (Phase 1-5) を実装
2. 名前空間を実装する際に、DotAccess の名前空間解決ロジックを追加

利点: 構造体のフィールドアクセスが先に動作する
欠点: 名前空間実装時に DotAccess 解決ロジックの追加が必要

### パターン B: 名前空間を先に実装

1. 名前空間を DotAccess 方式で実装
2. 型システム実装時に DotAccess に構造体フィールドアクセスの分岐を追加

利点: 名前空間が先に使えるようになる
欠点: 名前空間の実装計画を変更する必要がある

### パターン C: 同時に実装

1. DotAccess の tree_parser 部分を共通で実装
2. 意味解析の名前空間解決と構造体フィールド解決を同時に実装

利点: 統一設計で衝突を回避
欠点: 作業量が大きい

**推奨: パターン A**

型システムの設計を先行し、名前空間タスクの方式を後から統合する。名前空間タスクの実装計画にこの依存関係を追記する。

## 命名規則の指針

衝突リスクを低減するための命名規則:

| 種別 | 命名規則 | 例 |
|------|----------|-----|
| 構造体名 | 大文字始まりの PascalCase | `MyStruct`, `Point` |
| 名前空間名 | 大文字始まりの PascalCase | `MySpace` |
| 変数名 | 小文字始まりの snake_case | `my_var`, `point` |
| 関数名 | 小文字始まりの snake_case | `my_func` |

構造体名と名前空間名の命名規則が重なるが、これらは異なるシンボル種別として管理されるため、意味解析で区別可能。
